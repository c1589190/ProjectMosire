三条必做（不做就全线 fail-closed）：

  1. 权限面显式表态 workspaces / docs / docs-edit 三个命名空间 —— 未表态 = 什么都做不到（不是"缺省放行"）；

★★ 升级前先读 §5.4：0.2.0 与当时的 ~/SimulatorMosire 源级不兼容（2026-10-17 实测编译红，非猜）—— AgentTool 新增的 default Set<String> roles() 与消费方既有的 SimosTool.roles()（Set<ToolRole>）同名同擦除、返回类型不兼容。 升级到本页当前版本前，请先按 §5.4 核对这条撞名是否已经处置。

2. 相对 0.1.0 的变更点（★ 消费方先看这节）

这是 0.2.0 那一版的实测窗口（tag v0.1.0 2026-10-14 → 发布点 2026-10-17），属历史记录： 比 0.2.0 更新的版本，其变更点要看仓库里的发布说明，本页不代拟。 核实方式：git log/diff v0.1.0..HEAD -- <模块>。

库窗口内改动（实测）对消费方意味着什么

行为面要留意的三条：

  1. Ask 有了第二条路：ToolCallAuthorizer 新增"待裁决队列"入口 （DECISION_QUEUED 具名码）。★ 用 ToolCallAuthorizer.standard() 的既有装配行为逐字不变 （该重载把队列位传 null）；只有显式接入待裁决队列的装配才走"登记进决策包、不执行"。
  2. 新增三个公开常量：ToolCallAuthorizer.DECISION_QUEUED / DECISION_RELEASE_UNKNOWN / DECISION_RELEASE_USED —— 子体侧靠码（不是文案）识别。
  3. /api/approvals 本版仍在、未删；但它已被用户裁定 16 判为"彻底删除" （设计-决策包作为唯一决策单元.md §5octies，含受影响清单）。⇒ 消费方不要新增对该面的依赖； ~/SimulatorMosire 现在依赖了它（Shell.java:1287、GuiServer.java:2210 透传、 AgentLibAvailabilityTest.java:61 钉 FQN），退役时要同一批改（跨项目破坏面）。

3. 必填的权限面（未表态 = 什么都做不到）

AgentPermissionSet perms =
    AgentPermissionSet.builder(AccessToken.SYSTEM)   // 或 DEFAULT
        .allowAll()
        .destructiveAllowed(true)                    // ★ 写文档必须
        .resourceScopes(new ResourceScopeMap(Map.of(
            "workspaces", ResourceScope.ofDir(root),  // ★ 建挂载必须
            "docs",       ResourceScope.ofDir(root),  // ★ 读文档必须
            "docs-edit",  ResourceScope.ofDir(root)))) // ★ 写文档必须
        .build();
  • 三个命名空间各自独立：只表态 docs 而没有 docs-edit ⇒ 读得到、写不了（反之亦然）； 一个都不表态 ⇒ 连挂载都建不了。
  • sensitiveAllowed(true) 同理按需显式表态；放行不得多于父级（spawn 时的单调性规则）。
  • 资源声明与判定在代码里的两处真值：DocsCapability.Manifests.READ/WRITE （docs / docs-edit，缺省 DENY）、WorkspaceTools 的 MANIFEST（workspaces，缺省 DENY）。
  • workspace_info 与 doc_guide 刻意不声明任何资源面 （ResourceManifest.NONE）——面空/未表态的调用者照样能调它们，否则"自救渠道"对最需要它的人关门。

5. 可用性钉：消费方侧那条测试怎么跑（★ 先说清"哪条钉钉住了什么"）

5.1 ★★ 现状事实（与仓库 AGENTS.md §0.5 的原文流程有出入，属 doc drift）

  • 消费方 ~/SimulatorMosire 现在钉的是固定版 0.1.0，不是 SNAPSHOT： pom.xml:108 <agentlib-mosire.version>0.1.0</agentlib-mosire.version> （三个库共用这一个拼写点；simos-app/pom.xml:117-123 用 ${agentlib-mosire.version} 引 docs/workspace）。
  • 实测解析结果（./mvnw -o -q -pl simos-core dependency:tree -Dincludes=io.mosire:agentlib-mosire）： \- io.mosire:agentlib-mosire:jar:0.1.0:compile； ~/.m2/.../agentlib-mosire/0.1.0/_remote.repositories 写明来自 mosire-pages。
  • ⇒ ./mvnw -pl AgentLibMosire -am install + AgentLibAvailabilityTest 这条既有流程， 在当前钉法下验不到本仓新代码：install 装的是 0.1.0-SNAPSHOT，而消费方解析的是 Pages 上的 0.1.0（实测该 jar 里 io/mosire/agentlib/decision/ 类数 = 0）。 它只证明"0.1.0 那个制品能加载"，不再证明"本仓今天的改动能加载"。改法待控制方裁定。

5.4 ★★ 实测：0.2.0 与当时消费方源级不兼容（roles() 撞名）——升级前必须先处置

证据：./mvnw -pl simos-core -am -Dtest=AgentLibAvailabilityTest -Dagentlib-mosire.version=0.2.0 -U test （先把 ~/.m2 里的 0.2.0 目录清掉，强制从 Pages 真下载：日志里可见 Downloaded from mosire-pages: …/agentlib-mosire-0.2.0.jar (389 kB)）⇒ BUILD FAILURE，退出码 1，红在 simos-ga-spi 的 compile，不是测试断言：

[ERROR] .../simos-ga-spi/src/main/java/io/mosire/simos/ga/spi/SimosTool.java:[35,17] roles() in io.mosire.simos.ga.spi.SimosTool clashes with roles() in io.mosire.agentlib.tool.AgentTool
[ERROR]   return type java.util.Set<io.mosire.simos.ga.spi.ToolRole> is not compatible with java.util.Set<java.lang.String>
[ERROR] .../simos-ga-spi/src/main/java/io/mosire/simos/ga/spi/SimosToolAdapter.java:[120,24] roles() in io.mosire.simos.ga.spi.SimosToolAdapter cannot implement roles() in io.mosire.agentlib.tool.AgentTool

根因（两侧都回代码核过）：

  • 本仓：AgentTool 在 0.1.0→0.2.0 窗口内新增 default Set<String> roles() （AgentLibMosire/src/main/java/io/mosire/agentlib/tool/AgentTool.java，角色维 RA4； 判定点 PermissionChecker:87、RoleCatalogAudit:120/283、ToolExecutionGuard:49 读它）。
  • 消费方：SimosTool extends AgentTool 早就声明了 Set<ToolRole> roles() （simos-ga-spi/.../SimosTool.java:35，实现 SimosToolAdapter.java:120）—— 同名、同擦除（Set）、返回类型不兼容 ⇒ javac 直接拒。
  • 语义也不同：AgentLib 侧角色名是不透明字符串（Set<String>），消费方侧是强类型枚举 ToolRole。

候选处置（三条，均需控制方裁定；本条不代拟）：

  1. 本仓改名（如 AgentTool#declaredRoles() / toolRoles()）⇒ 消费方零改动； 代价是本仓公开面改名 + 新版本号，且 AGENTS.md §0.5 的"被钉类不得改名"只管类、不管方法；
  2. 消费方改名（SimosTool#roles() → 另一个名字）⇒ 本仓不动；代价是消费方大面积改 （roles() 是它 44+ 工具的"唯一拼写点"）；
  3. 消费方把返回类型对齐 Set<String> ⇒ 丢掉强类型枚举，风险最大，不推荐。

★ 无论选哪条，§5.1 那个缺口都是这次没能在发布前抓到它的直接原因： 按老流程跑 install + AgentLibAvailabilityTest 会全绿（因为解析的还是 0.1.0）。

6. 常见坑（每条带原始报错文案）

#现象（原始文案）原因 / 解法
1M1: 物理范围不在调用者的 workspaces 可达面内（缺省 DENY：未表态 = 一个挂载都建不了） 没表态 workspaces
2PERMISSION_DENIED: 工具 doc_create 为破坏性操作，需显式放行 没 .destructiveAllowed(true)
3RESOURCE_DENIED: 该调用者够不着这个工具声明的任何资源 没表态 docs / docs-edit
4WORKSPACE_NOT_FOUND: 工作区不存在或不可见: xxx ToolContext.identity().instanceId() 必须 == 挂载的 user（"不可见"与"不存在"刻意同码）
5M2: 只能为自己或自己的后代创建工作区 替别人挂载要走正规血缘路径（holder=父、user=子、落点在父工作区内）
6纪律不符（B9）：list 需要 LOG 纪律的挂载 DocsApi.list 只服务 LOG；FILE 的直接子项列举走 WorkspaceRegistry.list()（投影）
7DOC_NOT_FOUND 但"文件明明在" 可见性判据（《接入指南》§5）：owner/tags/affiliations 三轴 + fail-closed 兜底
8物理路径不出现（不是报错，是约定） 面向模型的输出只含虚拟路径（WorkspaceTools 的 A7/G4、DocsTools 的 G4/A7）； mount_workspace 只接受派生形态
9noExport 与两个外发面都求交 AgentToMcpServer.exportable(tool, include) = include.test(name) && !spec.noExport() （AgentToMcpServer.java:804-807），且初始注册 / 列表 / 增量同步三处同源 （:727、:777、:790）⇒ 子体 MCP 桥与外部 MCP 面都受 noExport 约束。
★ 历史教训：曾有一版记录把"noExport 只挡子体桥"写成机制描述，随后被更正 （MainMosire/.../app/AppMcpLinkTest.java:160-177 的收口单）。 想彻底不外发 = 级别 + noExport 两道（级别挡判定面、noExport 挡结构面）
10决策面 POST 回 404 {"code":"PACKAGE_NOT_FOUND"} 决策面对在途包（跨进程临时包 xp-…）的写路由要求装配方接上"在途写口"； 没接（null）时详情面只认包登记表、写路由一律 404 （DecisionPackagesHttpHandler.java:115、:439、:594、:643）。 生产装配 App 已接（App.java:866、:870）

维护方：怎么发新版

git tag -a vX.Y.Z -m "…" && git push origin vX.Y.Z   # tag 触发 .github/workflows/publish-maven.yml
# 或在 Actions 页 / gh CLI 手动 dispatch publish-maven 并填版本号：
#   gh workflow run publish-maven.yml -f version=X.Y.Z

工作流做四件事：versions:set 定版本 → 只构建/部署「父 pom + 三个库」到暂存目录 → 校验布局（父 pom 与三库的 jar/pom/sources 必须齐，缺一个就红）→ 推 gh-pages （keep_files=true ⇒ 历史版本保留，消费方可钉旧版）。

★ 本页的版本参数化：页面源码（仓库内 pages/index.html）里凡是当前版本号的地方都写成占位符 __MOSIRE__VERSION__；工作流在"带上落地页"这一步用本次发布的版本号 sed 替换后再拷进暂存目录 （替换后若还残留占位符会直接失败）。⇒ 发新版不再需要手工改这张页面，也不会再出现"发了 0.2.0、门面仍写 0.1.0"的漂移。
