## 〇、范围重排说明（为什么调头）

用户 2026-09-12 晚的新指令：**"bash 的话，先给主Agent做个全功能（默认拦系统级，权限确认的话，要不现在就做掉？cli 直接 yes/no，http api 也要有权限确认方法方便调试）"**。

调头后的判断（依据 `设计-审批与工具内权限.md` §一）：
1. **bash 是第一个能把"模型自造字符串"变成任意副作用的工具**——目录围栏（防子体越界）保护不了"主 Agent 自己把系统改了"；
   对主 Agent 而言，**审批（人）**才是对应的那一层。⇒ 审批先做，围栏后做，**顺序比原计划的更对**。
2. **判定点不统一的洞**：MCP 路径（`AgentToMcpServer.handleCall:257`）今天**直接 `tool.execute`**——审批若只落在管线，
   一旦 bash 下放给子体（S5 裁决 ⑤）就会出现"子体经 MCP 调 bash 完全无审批"。⇒ 本段**先收敛判定点**，S5 才谈下放。
3. 目录围栏/身份穿透/沙箱那四块（原 A/B/C/D 块）**硬依赖"检查锚到调用者"**（原调查 §1.4 的锚点缺陷），
   与 `bash-for-main` **零依赖**——拆开做不增加返工，反而各自更小。

## 一、目标与范围

**做**（三块 + 验收，按依赖顺序）：

- **A 判定点统一**：新增 `ToolCallAuthorizer`（`AgentLib`，guard + 审批 +（S5 加资源判定）的唯一入口）；
  两个调用点同批改：`AgentPipeline.executeToolCall:782`（`guard.execute` → `authorizer.execute`）与
  `AgentToMcpServer.handleCall:257`（裸 `tool.execute` → `authorizer.execute`）。
  ⇒ **结构性收获**：`PermissionChecker` 的三要素位（sensitive/destructive/白名单/身份级别）在**子体路径上第一次真正生效**。
- **B 审批内核**：`ApprovalGate` 链（`DenyGate`/`AutoApproveGate`/`ConfirmGate`）+ `ApprovalRequest`/`Decision` +
  `PendingApprovals`（内存、幂等、超时）+ 两通道（**tty** 直开 `/dev/tty` yes/no；**HTTP** `GET /api/approvals` /
  `POST /api/approvals/{id}`）+ 事件落账（脱敏）+ **fail-closed**（超时/无通道/通道异常 ⇒ 拒）。
  语义红线：**审批 ≠ 授权**（不写回权限集、不被子体继承）、**硬拒不进审批**、`APPROVE_SESSION` 的键是 `classKey` 不是工具名。
- **C bash 主 Agent 全功能**：注册 `ShellTool`（`App.java:414-418`）+ `BashCommandClassifier`（三档：`BLOCKED`/`ASK`/`ALLOW`，
  内置清单见设计附录 A，配置**只增不删**）+ 命令落账脱敏（`tools.bash.commandLog = digest|full`，默认 `digest`）。
- **D 使用模式验收 V1~V9**（设计 §五，**真模型 + HTTP 实时审批**）。

**不做**（本段明确排除）：
- 目录围栏 L1/L2/L3、身份穿透、`SubagentInstance.parentInstanceId`、`agents.*` 预算、子体派发开放 —— **归 S5**；
- 插件内数据权限 SPI 的**实现**（接口形状本段定死，实现归 S5）；
- 命令字符串完备防线 / 禁词表穷举（假防护，设计 §2.1）；
- 审批的 `always`（持久化）、AG-UI HITL 面、跨进程审批；
- **子体用 bash**（出厂模板默认不给；下放归 S5，前提是本段 A 块已让 MCP 路径过 authorizer）。
