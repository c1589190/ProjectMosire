## 三、设计

### A. 血缘与判定（D27 主体）

1. **血缘载体**：`SubagentInstance` 增 `lineagePath`（`main/a1/a1-1` 形态，段分隔符固定）；**由父在派发时拼**（父 path + 子 id），
   子不可改（I4）。**不经 argv**（2026-09-13 设计文档更正）：判定全部发生在父进程（子体的工具都经 MCP 打回父侧执行），
   且 S5-A 起 `ToolContext.identity` 已带 `instanceId` ⇒ 调用者 path 查表即得，不需要第二份来源。
   `parentInstanceId` 保留为直系事实来源（S5-A 已加），`lineagePath` 只作**前缀匹配**用，两者不从属、不互推。
   详见 `设计-身份与血缘.md` §二。
2. **调用者身份**：判定读 `ToolContext.identity.instanceId`（S5-A 已到位），**不读 token**（两个维度不许合并成一个数字）。
   `capabilities(c)` = 该实例的权限集（从 `SubagentManager` 查实例，与 `SubagentInstance.permissions` 同源）。
3. **判定式**：`允许(c, t, op) ⟺ op ∈ capabilities(c) ∧ t ∈ subtree(c)`，落点**只在** `ContextAccessJudge`（`self` 仅当调用者是 main 或已知实例时放行）：
   完整规则表（6 条 fail-closed）见 `设计-身份与血缘.md` §三.3；
   - `subtree(c)` = `lineagePath` 的**按段前缀匹配**（含自身）。**必须按段匹配**——否则 `a1` 会命中 `a10`（判别性要点，变异即转红）；
   - `capabilities(c)` = 逐跳只减不增（S5-A 的 `tightenPermissions` 已是这条）。
4. **`kill` / `list` 从 `systemOnly` 开放到判定**：删掉工具内 `caller == SYSTEM` 自查，改为走 `ContextAccessJudge`（第 3 条）；
   拒因必须是"`a1-1 ∉ subtree(a2)`"，**不许**是"工具不存在"（V2 判据）。
5. **`read_agent_context` 的读侧同判（本段唯一的"结构性 → 判定性"降级，要点名）**：今天它靠 `noExport` **结构上**进不了子体；
   V4 要求 a1 能读 a1-1 ⇒ 必须去掉 `noExport`、靠判定守。**代价**：跨血脉读取从"不可能"变成"被拒绝"，
   判别性完全压在 `subtree` 判定 + 用例上。**已由用户裁决 + `设计-身份与血缘.md` §四定死**（反例用例见该文 §七；若日后要收回，退路是恢复 `noExport` 并改写 V4 为"a1 不能读 a1-1"）。
6. **`A1` 派发自定义（原 §1.4）**：`spawn_sub_agent` schema 增 `allowedTools`（可选数组）；
   不指定 ⇒ **模板建议**（现状兼容，逐字不变）；指定 ⇒ 生效值 = **模板白名单 ∩ A1**（请求面只收窄，同 `allowedDirs` 口径），
   且 **A1 ⊆ 调用者能力集** 是 `spawn` 入口的结构性硬检查，违者**派发即拒**（`SubagentRejectedException` + 既有错误码体系，事件**点名**越界工具）；
   `SubagentLaunchRequest` 增字段 + 兼容构造；空表 = 显式"什么都不给"（与 `allowedDirs` 同形同义）。详见 `设计-身份与血缘.md` §五。
7. **反例测试必须结构性**：`a2 不能动 a1-1` 的理由必须是 `subtree`，不许靠"工具表里没有"。

### B. 终局与"等/取"口

1. **前置：`stopReason` 入持久面**（没有这条，`wait` 等到了也交不出 V7 要求的东西）：
   子体在退出前把 `stopReason` + `turns` + `toolCalls` 落进**自己的 `events.db`**（`agent.lifecycle action=finished` 形态，
   与既有事件口径同构），**先落库 flush 再退**；异常退出（非零退出码 / 该事件缺失）⇒ 父侧映射"异常终局"并带退出码。
   备选（不推荐）：新增 MCP 回报协议面——多一条线上契约，收益相同。
2. **子体跑完即退**：`SubagentProcessMain` 去掉/条件化 `whenClosed().get()`；`chat()` 返回 ⇒ 落① ⇒ 正常退出 0。
   保留的语义：`kill` 时父侧先关 server ⇒ 子体可能来不及落库 ⇒ 父侧按 `KILLED` 记（不假装有 stopReason）。
3. **`wait_sub_agent(instanceId, timeoutMs)`**：等到终态或超时返回；返回体含 `status` + `stopReason` + `turns`/`toolCalls`（+ 异常时的退出码）；
   实现复用既有退出观测（把私有 `awaitDead` 升为"等终态"的公开口，`SubagentManager.java:993-1006`）；判据 = `subtree`（第 A.3 条）。
4. **`list_sub_agents` 增终态字段**；**`kill_sub_agent` 返回终态**（C 档登记项同批修，`progress.md:142`）。
5. **`SubagentManager.close()` 由深到浅关停**（按 `lineagePath` 深度排序，`SubagentManager.java:358-365`），保"父崩时有人收尸"与跳级处置。

### C. 观测面一致性

`onChildExited` 对 RUNNING→已退出不再一律 `FINISHED`：按退出码/诊断区分正常/异常终局，**模型面可见**
（`list`/`wait`/快照都带；父库 `agent.lifecycle` payload 带原因），运维面日志保持（S5-E D2 的 WARN 不动）。
状态机**不新造状态**，只加"终局原因"字段（具体字段名在设计文档里定）。
